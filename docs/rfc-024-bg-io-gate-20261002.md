# RFC 024: background-I/O gate — measured, rejected

**Decision:** Reject. The gate is a correct implementation of the design, but the
design's premise is contradicted by the trace: background bursts almost never
start during a WAL sync, and the batch tail is a property of concurrent fsync
streams on this ext4 device that background *pacing* cannot remove.

**Run date:** 2026-10-02. Host: Linux 6.18.9-arch1-2, existing ext4 mount
(`/home/liu`, nvme0n1p3, scheduler `none`). Release binary built with
`--features bench --bin write-perf`, snapshotted before timing:

```text
sha256 3fe356566cf473418aa013bb33fbebecce44c0691bc1aea1b8bd3517663d8af0
```

## What was built

`kv-engine/src/bg_io.rs`, enabled by `KV_WAL_IO_GATE` (default off, so both arms
ran on one binary):

1. **One background write burst at a time** — a shared token taken around
   `FileObject::create`, the single choke point every SST write funnels through
   (flush and compaction).
2. **A sync gate** — a burst waits (bounded at 2 ms) while a WAL `fdatasync` is
   in flight. The WAL side marks syncs in flight on the leader path, the
   parallel publisher path, and the legacy buffered path. Foreground never
   waits for background.
3. **Idle bypass** — with no completed WAL sync in the last 10 ms, a burst does
   not pace at all.

Unit tests cover the token, the counter, the bounded wait, the drain case, and
the idle bypass; the full in-crate suite (1252 tests) passes with the hooks in
place and the gate off.

## Why it cannot work here

**Trace.** With `KV_WAL_IO_GATE_TRACE=1` on the failing shape, the run produced
59 background bursts: **58 started with no WAL sync in flight**, one waited
(324 µs). The gate is engaged and has almost nothing to gate against.

**Profile.** The same shape under `--profile`: 319 commits, 319 syncs,
`fdatasync_ns` 116 ms total (≈364 µs mean), `preallocation_ns` 2.8 ms. So the
typical sync is short and a handful are ~20 ms; the p99 is those few long syncs,
each of which delays the ~205 puts that share its group.

**The tail is fsync-stream concurrency, sized by neither write batch nor
metadata.** A standalone probe on the same filesystem, where the measured thread
`fdatasync`s a preallocated file and a background thread generates load:

| background load | p50 | p99 | p99.9 | max |
| --- | ---: | ---: | ---: | ---: |
| none | 507 µs | 1.17 ms | 1.3 ms | 1.3 ms |
| create+write+fsync+unlink 2 MiB files | 996 µs | 2.3 ms | 2.6 ms | 37 ms |
| write+fsync into one preallocated file | 1028 µs | 2.48 ms | 26.7 ms | 27 ms |
| … same, 256 KiB background fsync batches | 1071 µs | 2.47 ms | 26.9 ms | 28 ms |
| … same, 64 KiB background fsync batches | 1080 µs | 2.48 ms | 26.6 ms | 29 ms |

Any concurrent fsync stream on this device produces 27–37 ms `fdatasync`
outliers, and shrinking the background fsync batch by 32× does not move them.
File creation is not special: the pure data+fsync case is equivalent.

Together: the long syncs are not caused by a burst *starting* during a sync
(which the gate controls), but by a sync *arriving* while a background fsync is
in flight (which it cannot). No amount of burst-start pacing changes that.

## Fixed comparison

Arms: A = gate off (`KV_WAL_IO_GATE` unset), B = gate on (`=1`). Same binary,
same case (ext4, 8 writers, batch 64, 65,536 puts, 2 MiB target SST), three
ABBA blocks, two scored runs per arm per block, one warmup per arm per case,
fresh path per run. Control screen: throughput max/min ≤ 1.05 and p99 max/min
≤ 1.10 within a block and arm.

| block | A ops/s | B ops/s | throughput ratio | A p99 ms | B p99 ms | p99 ratio | control |
| ---: | ---: | ---: | ---: | --- | --- | ---: | --- |
| 1 | 169,385 | 195,745 | 1.156 | 22.77 / 35.35 | 21.99 / 19.87 | 0.737 | fail |
| 2 | 202,470 | 196,637 | 0.971 | 18.20 / 21.07 | 20.11 / 25.31 | 1.152 | fail |
| 3 | 189,371 | 182,574 | 0.964 | 22.54 / 23.14 | 30.08 / 18.37 | 1.029 | fail |

Median throughput ratio **0.971** (2.5/97.5 interval [0.964, 1.156]); median p99
ratio **1.029**. The p99 ratio moves in both directions across blocks (0.737,
1.152, 1.029) and the acceptance target — p99 from ~23 ms toward the ~3 ms the
device shows when unloaded — is nowhere in evidence. All three control screens
fail on the host's usual within-arm spread, as in the earlier records; all
blocks stay in the score.

**Verdict:** reject. The gate neither improves the tail nor costs a measurable
amount of throughput; it simply does not address the mechanism.

## What does move the tail

The measured levers that remain are the ones already attributed:

- **Fewer flush events.** 64 MiB and 1 GiB target SSTs measured p99 3.4 ms and
  2.35 ms with *higher* throughput (292k/375k vs 187k ops/s) — but the default
  SST size was already tested at 2/4/8 MiB and rejected (p99 23.2/21.8/28.9 ms,
  non-monotone), so this is a workload/format tradeoff, not a free fix.
- **Nothing else tried.** Submit mechanism (parity), compaction (no effect),
  preallocation (2.8 ms total), background batch sizing (no effect), and now
  burst-start pacing (parity) are all excluded by measurement.

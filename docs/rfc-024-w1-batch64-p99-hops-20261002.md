# RFC 024: 1-writer batch64 tail and pipeline-hop measurements

**Decision:** The qualification's `ext4-batch64-w1` p99 regression (+42.1%) is
reproduced directionally in this same-session comparison. The parallel path's
additional serial stages are measured, but these probes do not isolate their
tail contribution from kernel and device effects. The separate eight-writer
flush-pressure experiment measures a rotating workload and does not establish
the cause of the qualification's
WAL-isolated eight-writer tail.
The qualification's 1-writer p99 guard remains unmet. One of this comparison's
three blocks fails its repeat controls; consistent direction does not supply
a controlled causal explanation.

**Run date:** 2026-10-02. Same binary both arms, PR #370 head:

## Fixed comparison

Exact qualification case `ext4-batch64-w1`: 65,536 puts, 1 writer, batch 64,
1 GiB target SST (WAL-isolated, no flush or compaction), value 1 KiB, ext4. Arms
are `--wal-io-mode leader` (A) and `--wal-io-mode parallel` (B) on one binary;
three ABBA blocks, two scored runs per arm per block, one warmup per arm, fresh
path per run.

| block | leader ops/s | parallel ops/s | throughput ratio | p50 ratio | leader p99 | parallel p99 | p99 ratio | control |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 94,217 | 97,704 | 1.037 | 0.948 | 1.229 ms | 1.623 ms | 1.320 | pass |
| 2 | 93,214 | 96,475 | 1.035 | 0.948 | 1.206 ms | 1.528 ms | 1.267 | fail |
| 3 | 95,659 | 93,709 | 0.980 | 0.953 | 1.209 ms | 1.769 ms | 1.464 | pass |

Median throughput ratio 1.035 (near parity); **median p99 ratio 1.320 with all
three blocks above 1.26**. On ext4 the parallel arm's p50
is 5% *better*, and one parallel run reached a 30.4 ms max against the leader's
2.25 ms worst.

The same A/B on **tmpfs** is a diagnostic here, not a target:

| filesystem | throughput ratio | p50 ratio | p99 ratio |
| --- | ---: | ---: | ---: |
| ext4 | 1.035 | 0.948 | 1.320 |
| tmpfs | **0.841** | **1.126** | 1.234 |

With sync inexpensive, the parallel arm loses at the median, tail, and
throughput. This is consistent with pipeline overhead becoming more visible;
the different filesystem does not isolate its contribution to ext4's tail.

## The pipeline at one writer

Parallel profile, same shape: `commit_groups 1024`, `solo 1024 (100%)`,
`avg_bufs 1.00`, `pipeline_peak groups=1 outstanding_write_sqes=1`. The pipeline
never overlaps, so no concurrency amortizes its stages. Per commit: `wal_sync`
mean 420 µs of which `fdatasync` 310 µs (leader: 443 µs of which 354 µs).

`SYNC_COALESCE_WAIT` (400 µs, `wal/parallel/runtime.rs:34`) is **excluded**: at
one writer `coalesce_admitted_prefix` early-returns because
`written_frontier >= cutoff`, and the aggregates confirm no such wait is paid (a
400 µs per-commit wait would add ~400 ms to a 654 ms run).

## Per-hop probe

Temporary instrumentation (bench-feature only; reverted from the tree after the
measurement, patch kept at
`target/rfc024-1w-batch64-arms-20261002/hop-probe.patch`): one "last event"
timestamp per role — producer `admit`, worker `pickup`, worker `write_done`,
coordinator `sync_done`, producer `observed`. The four intervals are exact while at
most one group is in flight, which the profile's `pipeline_peak groups=1`
confirms for this shape.

| hop | ext4 run 1 (mean / max) | ext4 run 2 (mean / max) | tmpfs (mean / max) |
| --- | ---: | ---: | ---: |
| admit → worker pickup | 9.3 / 104.7 µs | 10.3 / 295.6 µs | 15.2 / 707.3 µs |
| pickup → write done | 97.8 / 1053.5 µs | 94.6 / 916.7 µs | 17.3 / 255.8 µs |
| write done → durable | 311.8 / 963.0 µs | 317.5 / 961.8 µs | 4.7 / 125.3 µs |
| durable → producer observed | 8.4 / 103.7 µs | 8.5 / 89.6 µs | 2.9 / 107.1 µs |
| total mean | 427 µs | 431 µs | 40 µs |

The ext4 total matches the profile's `wal_sync` mean (420 µs), so the split
covers the whole commit wait. One 41 ms `pickup → write done` outlier appeared in
an earlier probe run and did not recur; it is episodic, not systematic.

## Tail ownership, and a refuted fix

Counting samples above 500 µs per 1,024 commits (same shape, ext4, parallel arm,
with the same probe extended to the leader path's own stages):

| stage | leader | parallel |
| --- | ---: | ---: |
| write stage (submit → CQEs reaped) | 1 | **50** |
| sync stage | 82 | 149 |

This probe counts 50 parallel write-stage samples above 500 µs against one
leader sample for the same 68 KiB direct-write shape. It does not establish a
general 50× tail probability. One possible contribution was the wait
mechanism: the leader reaps completions inside a blocking
`io_uring_enter` (`submit_and_wait`), while the worker sleeps in
`poll(ring_fd, wake_fd)` and reaps after a separate wakeup.

**Prototype and result:** the worker's wake eventfd was registered with the ring
(`register_eventfd`, prototype gated by `KV_WAL_WORKER_EVENTFD`) so that one fd
covers both completions and commands and the ring fd is not polled. Three paired
runs per arm:

| arm | p99 (3 runs) | write-stage tail samples | write-stage tail max |
| --- | --- | ---: | ---: |
| ring-fd poll | 1.80 / 1.86 / 1.68 ms | 48 / 53 / 50 | 1.34 / 1.16 / 0.96 ms |
| registered eventfd | 1.88 / 1.91 / 1.67 ms | 50 / 55 / 53 | 1.16 / 27.4 / 0.68 ms |

No improvement, and one eventfd run produced a 27 ms write-stage outlier. This
rejects the measured registered-eventfd variant, which still used an external
wait. It does not locate the stall inside the kernel or exclude other completion
delivery designs. The prototype is reverted; the patch is kept in the artifacts
directory. Later [cooperative](rfc-024-ring-command-wait-20261003.md) and
[deferred](rfc-024-deferred-ring-wait-20261003.md) native completion-wait screens
also fail their fixed retention target.

## Mechanism

The parallel path serializes four stages on the critical path — queue/handoff
(~10 µs), worker write submission and completion (~95 µs on ext4, 17 µs on
tmpfs), coordinator `fdatasync` (~310 µs on ext4, ~5 µs on tmpfs), and producer
wakeup (~8 µs) — where the leader path runs write and `fdatasync` inline in the
submitting thread. Tmpfs exposes a measured throughput and median-latency cost
(−16% throughput, +10 µs p50). The ext4 observations identify additional serial
intervals but do not establish an additive p99 budget: interval maxima and
end-to-end percentiles cannot be summed to attribute the regression.

In these probe samples, producer wakeup (8 µs mean, ~100 µs max) and queue
handoff (~10 µs mean) are smaller than the write/sync intervals. The conditional
coalescing wait is not paid at this one-writer cutoff, as described above.

## Implication for the RFC gate

The one-writer p99 cell misses the RFC guard. At one synchronous writer there
is only one outstanding commit, so the pipeline cannot amortize its stages
through group concurrency. A useful optimization must reduce this path's cost
while preserving durability and multi-group progress. These measurements do
not prove that switching a lone writer to another backend is necessary; no
production selector is introduced.

## Durability barrier diagnostics

With the hop split known, the remaining question was which stage to optimize.
Three measurements, all on the 1-writer batch64 shape:

**Task states** (`/proc` sampling, ~3,400 sweeps per run; `perf record` and
`--per-thread` do not work on this host): the WAL worker spends ~0% of samples in
`D`, waiting instead in a futex (idle, between groups) or
`poll_schedule_timeout` (a write CQE outstanding). An asynchronous-I/O issuer
can sleep in poll while device I/O is outstanding. Thread state alone cannot
distinguish device service, kernel completion delivery, and scheduling delay.

**Device stats** (`/proc/diskstats`, 262,144 puts): the parallel run records
*fewer* whole-device writes than the leader run (11,549 vs 13,085) at a lower mean write
time (0.67 vs 0.83 ms). These counters cover the whole device and do not
independently attribute work to the WAL or establish device isolation.

**Extent conversion** (standalone probe, `fsync_extent_probe.c`, 64 MiB
fallocated file, 68 KiB writes, one `fdatasync` each):

| sample | p50 | p90 | p99 | max |
| --- | ---: | ---: | ---: | ---: |
| first write into a fresh 1 MiB prealloc block | 498 µs | 828 µs | 1,086 µs | 1.1 ms |
| already-converted space | 495 µs | 567 µs | 1,160 µs | 34.7 ms |

The median floors are similar, and a 34.7 ms outlier occurs in already-converted
space. First-touch extent conversion is therefore not necessary for such an
outlier. This standalone probe demonstrates sync variability but does not
quantify the preallocation cost or tail attribution in the live engine.

Per-commit durability still requires a barrier, and one synchronous writer
provides no later commit to group with it. The serial stage measurements guide
further experiments; rejected variants do not establish that every engine-side
optimization is exhausted. The full performance gate still requires a controlled
end-to-end comparison.

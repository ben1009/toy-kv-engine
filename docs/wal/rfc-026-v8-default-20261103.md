# V8 PITR WAL default adoption — 2026-11-03

The maintainer selected V8 as the default PITR writer on 2026-11-03. This is
an explicit adoption decision while the RFC 026 performance matrix remains
unqualified. It does not establish V4/V7 parity or turn unmatched SSD-state
measurements into a performance result. See the
[calibration report](benchmarks/rfc-026-v8-calibrated-states-20261103.md) for
that limitation.

## Selection

`LsmStorageOptions::pitr_writer_format` defaults to `PitrWriterFormat::V8`.
A successful `enable_pitr` installs V8 before reopening commit admission.
V8 uses Parallel I/O by default; `open_with_wal_io_mode(..., WalIoMode::Leader)`
continues to select the serial comparison path. V8 Parallel normally uses
`O_DIRECT`; when the filesystem rejects it as unsupported, DATA uses a buffered
worker handle with the same FRONTIER and `fdatasync` durability ordering.
Ordinary, non-PITR databases continue to create V4 WALs with Parallel I/O.

The public enable path uses the existing durable V6 → V7 → V8 bootstrap
transitions. It publishes the PITR base, reserves migration resources, seals
each predecessor, and installs the exact manifest-authorized successor. The
V8 compatibility guard is durable before the first V8 migration record.
No existing segment is relabeled or rewritten as another format.

On Linux ext-family filesystems, V8 Parallel with an `O_DIRECT` DATA worker
uses quota-accounted 1 MiB sliding `fallocate` windows. The image's source-spool
quota reserves the unused window suffix; if that extra capacity is unavailable,
allocation covers only the currently reserved DATA/FRONTIER range. If window
slack later blocks batch admission, the coordinator durably trims the unassigned
suffix, releases its quota, and retries with exact allocation for the rest of
the segment. Admitted DATA and reserved FRONTIER ranges remain intact; failed
truncation or sync retains the slack charge. This prepares
filesystem extents only: it does not zero-initialize them or advance durability.
Filesystems outside this scope and buffered DATA fallback retain the existing
write path. Active recovery normalizes the image to its accepted boundary, so
an unused preallocated tail is discarded. This runtime behavior has not yet
qualified V8's performance matrix.

`write-perf --pitr` now uses this same public V8 path in normal Linux builds.
`--pitr-format v6` and `--pitr-format v7` retain explicit compatibility controls;
`--wal-io-mode leader` remains available independently. The benchmark drains
startup maintenance before its timed workload.

For library comparisons, set the preference explicitly:

```rust
use kv_engine::lsm_storage::LsmStorageOptions;
use kv_engine::pitr::api::PitrWriterFormat;

let options = LsmStorageOptions {
    enable_wal: true,
    pitr_writer_format: PitrWriterFormat::V7,
    ..LsmStorageOptions::default_for_test()
};
```

V6 keeps the legacy writer. V7 retains the legacy bootstrap and its eligible
V6-to-V7 rotation/resume migration. A preference is not a downgrade command:
opening an existing V8 database with V6 or V7 selected retains V8.

## Existing databases and capacity

With a repository configured, synchronous, asynchronous, and repair startup
resume eligible legacy/V7 PITR databases toward V8. Explicit `resume_pitr`
also performs these migrations. Pending archive obligations must settle first;
regular rotations otherwise retain their existing format until a later
eligible resume.

Existing databases whose persisted limits cannot fund a migration retain
their current format and remain writable. Legacy V5/V6 retains Leader I/O;
V7 retains its selected I/O mode. Filesystem capacity-sampling errors defer
migration rather than fencing a healthy older writer. Deferred adoption does
not silently increase persisted limits.

A new enable request must fund both bootstrap transitions, including retained
source allocations, seal sidecars, future Active image growth, recovery
workspace, and successor/staging/manifest headroom. Insufficient configured
capacity is rejected before repository creation or durable enable intent.
Actual transitions refresh the capacity estimate and reserve it before intent.
Publication or I/O failures after durable intent retain the recovery fence;
reopen/resume completes the recorded transition.

## Compatibility and retained behavior

V8 keeps RFC 025's DATA/FRONTIER frames and one WAL sync per durability
advance. RFC 026 adds encode-time BLAKE3 entry digests and the 113-byte ordered
link. Admission visibility precedes payload preparation; readiness gates
submission and durability. The retained grouping, coalescing, notification,
and published-cursor optimizations are unchanged by default selection.

Active recovery validates logical hard anchors and candidates before fallback
and fresh-inode normalization. Sealing and archive validation remain strict.
Historical reader rejection still relies on the durable compatibility guard;
selecting V7 later cannot make retained V8 WALs or archives readable by old
binaries.

The existing V7/V8 limitation on `disable_pitr` and `disable_pitr_allow_gap`
remains: these calls reject before mutation because transition back to an
ordinary WAL is not implemented. Use the explicit V6 preference when that
legacy lifecycle is required. Recovery points, checkpoints, archival,
backup/restore, and same-format V8 rotation use their existing V8 paths.

# RFC 026: P-core CPU attribution and allocator screen on the existing SSD

CPU investigation can continue on this machine without another SSD. This
round keeps all database writes on the existing ext4/Solidigm P41 Plus and
records CPU work separately from performance qualification. **All eight full
captures are storage-flagged.** They supply no new eligible best score and do
not demonstrate an SSD mitigation or a V7/V8 throughput comparison.

No runtime change is retained. In particular, the allocator screen does not
justify replacing the system allocator. The notification streams, single
durability driver and published cursor remain as retained in `b8da402a`.
Digest formulas, wire bytes, DATA grouping, sync policy and device settings
are unchanged. Background-role affinity remains
[unresolved](rfc-026-v8-background-affinity-20261102.md).

The fixed workload is 750,000 puts, sixteen writers, batch64, 1 KiB values,
Parallel WAL, no compaction, a 2 GiB SST target and latency sampling every ten
batches. All benchmark processes and their userspace child threads inherit
`taskset -c 0-15`. The separate profiler collector may use all CPUs. There
are **zero E-core userspace workload samples in every capture**; this is
observed sample placement, not an assumption from the allowed CPU mask.

The preserved producer-attribution executable is reused, with SHA256
`fbb90ea8a6f20bf476760e79ae60e04cda3edae04138d45ae5a9e6346da299f1`.
Its temporary instrumentation and build instructions are
[already archived](rfc-026-v8-producer-attribution-20261102.md).
No build or test runs alongside a measurement. The two cohorts each use a
15-second initial idle and three-second gaps. These pauses do not establish
that the controller is in an identical internal state.

The first cohort uses V7 → V8 → V8 → V7:

The filter is unchanged: p99 above 10 ms **or** mean fdatasync above 1 ms
flags a capture. Even the last V7 mean is above the threshold before rounding.
Stalls alter concurrency and publication costs; the variation between the
two identical V7 invocations prevents a causal format comparison.

Sampled phase estimates locate the following work. CPU values are seconds,
scaled separately for each thread by its actual call/sample counts:

| CPU scope | V7 00 | V8 01 | V8 02 | V7 03 |
|---|---:|---:|---:|---:|
| Logical encoding parent | 0.765 | 2.240 | 2.202 | 0.541 |
| Allocation/zeroing, inside encoding | 0.311 | 0.847 | 0.852 | 0.204 |
| Entry encode/CRC/hash, inside encoding | 0.404 | 1.271 | 1.235 | 0.301 |
| Physical frame materialization/CRC | 0.905 | 0.433 | 0.422 | 0.631 |
| V7 ordered logical SHA | 1.366 | — | — | 0.931 |
| Memtable publication | 2.654 | 3.134 | 3.190 | 1.974 |
| MVCC publication | 0.339 | 0.774 | 0.729 | 0.161 |

**Do not add encoding to its children.** V8 encoding includes its payload
BLAKE3; V7's ordered logical SHA is a separate scope. V8 payload hash estimates
are 0.898/0.909 s and ordered links only 0.0137/0.0145 s. Both V8 captures
hash exactly 787,500,000 entry-stream bytes with zero post-encode hash rereads.
The ordered digest is still not the main remaining CPU target.

The initial leaf profiles contain roughly 31–33% libc samples. Resolving the
native build ID and instruction offsets distinguishes allocation-related
synchronization sites, comparison/copy routines and zero-fill work. Four
specific verified lock/branch sites account for 8–10% of all userspace samples.
Their private function names are stripped: the evidence does not label all
libc work as allocation, nor infer that changing allocator saves that entire
share. This motivates one reversible allocator screen rather than a runtime
rewrite.

The second cohort runs **system → mimalloc → mimalloc → system**, all V8,
with the same executable, placement and workload. Installed native mimalloc
is package `2.2.4-1`, `mi_version()` raw value 224, library SHA256
`0480b3b2de1eea334388482e4e8554a318e0887d717a0dd684a8df74dce462bb`.
`LD_PRELOAD` applies only to the benchmark child, not the perf collector.
Symbol resolution verifies that malloc, calloc, realloc, free and
posix_memalign use mimalloc. Aligned allocation/content/free smoke checks
pass; samples in mimalloc confirm it also executes in the measured child.
No package installation, global allocator setting or Rust dependency changes.

| Capture | Process CPU, s | Peak RSS, MiB | p99, ms | Mean fdatasync, ms |
|---|---:|---:|---:|---:|
| 00 system | 8.459 | 909.9 | 25.884 | 1.732 |
| 01 mimalloc | 10.480 | 1,141.6 | 29.315 | 2.514 |
| 02 mimalloc | 10.184 | 1,142.6 | 30.927 | 2.423 |
| 03 system | 11.241 | 910.1 | 26.888 | 2.462 |

Peak RSS is `wait4` command-tree `ru_maxrss`: the maximum individual-process
RSS, including profiler and benchmark lifetimes. It is neither their sum nor
a timed-interval-only memory delta. Both paired comparisons show approximately
25.5% more peak RSS under mimalloc. CPU changes disagree: +23.9% in the first
pair and −9.4% in reversed order. Neither pair qualifies for throughput/p99
retention.

The four verified libc synchronization sites disappear under the override.
Nevertheless, MVCC publication leaf samples rise from 9.1–9.9% with the system
allocator to 15.0–15.7% with mimalloc; its sampled publication CPU rises from
0.604–0.788 s to 1.254–1.521 s. This is consistent with contention moving
elsewhere in the pipeline, but stalled diagnostics do not prove that causal
chain. Removing one sampled hotspot has not produced a repeatable whole-run
CPU saving. The allocator override is not retained.

All sampling uses `perf cpu-clock:u` at 499 Hz, enabled only during timed
writes through control FIFOs. Perf output stays in a memfd until the workload
ends, then is saved under this repository's local `target/` directory. Initial
smoke setup exceeded the existing perf memory-lock allowance with 256 pages;
64 pages passes without changing host limits. Two-format and two-allocator
smokes pass before full capture. Every full capture reports zero lost samples.
Optimized/assembly callchains are often only one frame; leaf instruction
counts are usable, but complete caller attribution is unavailable. CPU sample
shares describe userspace, not fractions of combined process user/system CPU.
Existing `bench` feature clocks also contribute work; this is not a build
without measurement overhead.

The [raw records](artifacts/rfc-026-v8-pcore-cpu-20261103-measurements.jsonl)
include result JSON, phase samples, exact commands, stderr, profiler headers,
libc mappings and local perf-file hashes. Compressed decoded stacks are
archived beside them. The
[analyzer](artifacts/rfc-026-v8-pcore-cpu-20261103-analyze.py)
recomputes the [summary](artifacts/rfc-026-v8-pcore-cpu-20261103-summary.json)
directly from those records and stacks. The
[plans](artifacts/rfc-026-v8-pcore-cpu-20261103-plans.json),
[format runner](artifacts/rfc-026-v8-pcore-cpu-20261103-run.py),
[allocator runner](artifacts/rfc-026-v8-pcore-cpu-20261103-allocator-run.py),

and [native identities](artifacts/rfc-026-v8-pcore-cpu-20261103-native-evidence.json)
preserve reproduction details. Runners were executed as `run.py` in local
`target/<experiment>/` and its `allocator-screen/` subdirectory; copying them
to the artifact directory does not change their recorded working layout.
The [check record](artifacts/rfc-026-v8-pcore-cpu-20261103-checks.json)
verifies archive integrity and that retained Rust sources remain unchanged.

Continue correctness and targeted CPU work on this SSD, preserving every
storage flag. There is no qualified SSD gain here, and no evidence to relax
durability or change production affinity. Publication/concurrency remains
worth investigating, but neither allocator replacement nor another digest
rewrite is supported by these results.

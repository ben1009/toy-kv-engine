# RFC 026 V7 vs V8 Direct/400 μs on GCP — 2026-11-11

## Result

On the same GCP host and Point workload, V7 Parallel reached a median 49.28k
puts/s, compared with 21.36k for V8 Parallel with Direct FRONTIER and the
fixed 400 μs coalescing budget. V7 was 2.31× faster; V8 reached 43.3% of V7's
throughput. The five counterbalanced blocks all favored V7, with paired block
median ratios from 2.19× to 2.31×.

V8 issued slightly fewer syncs, so sync frequency does not explain the gap in
this comparison. Its median per-run average `fdatasync` time was 104.5 μs,
versus 15.8 μs for V7. The median cumulative FRONTIER-write-plus-sync time was
1.082 s for V8 and 0.420 s for V7. V8 also used 1.91× the process CPU time.
These measurements narrow the remaining gap to the V8 durability and CPU
paths, but do not isolate a single cause.

## Setup and method

- Source commit: `66fd708d0a3d9e8069bb7fffac726683126df06b`.
- GCP `c4-standard-16-lssd`, 16 vCPUs, Intel Xeon 6985P-C, two NVMe Local SSDs
  in RAID0, ext4 mounted at `/mnt/test-ssd`.
- Each run performed 100,000 concurrent Point puts with 1 KiB values, 16
  writers, Parallel WAL, PITR enabled, a 2 GiB target SST size, and compaction
  disabled.
- V7 used `--pitr-format v7`. V8 used `--pitr-format v8`,
  `TOYKV_WAL_V8_FRONTIER_MODE=direct`, and
  `TOYKV_WAL_V8_COALESCE_BUDGET_US=400`.
- Five counterbalanced blocks ran four samples each in ABBA or BAAB order.
  This produced ten runs per arm. `--profile` and
  `--wal-sync-diagnostics` were off. Operation latency was sampled every 100
  puts, yielding 1,008 samples per run. Aggregate bench counters remained on.
- Every V8 run reported DATA and FRONTIER `O_DIRECT=true`, sync
  `O_DIRECT=false`, and stable same-inode handle metadata. V7 handle metadata
  is not emitted in the benchmark JSON; its Parallel constructor opens the
  WAL with `O_DIRECT` and clones that descriptor for worker, sync, and
  preallocation handles in [`wal.rs`](../../../kv-engine/src/wal.rs).

## Results

Medians are across ten runs per arm; ranges show the ten individual runs.
Latency values are sampled operation percentiles. The per-run cumulative I/O
value is the sum of aggregate FRONTIER-write and `fdatasync` timings.

| Metric | V7 Parallel | V8 Direct / 400 μs |
| --- | ---: | ---: |
| Throughput, k puts/s | 49.28 (44.36–49.58) | 21.36 (20.90–21.52) |
| Sampled p50, ms | 0.295 (0.289–0.309) | 0.740 (0.734–0.749) |
| Sampled p99, ms | 0.784 (0.685–2.954) | 2.026 (1.318–2.944) |
| Syncs per 100k puts | 8,235.5 (8,179–8,271) | 7,361.5 (7,218–7,483) |
| Per-run average `fdatasync`, median | 15.8 μs | 104.5 μs |
| Cumulative FRONTIER write + sync per run | 0.420 s | 1.082 s |
| Process CPU time per run | 5.91 s | 11.32 s |

Paired block medians also consistently show the V7 advantage:

| Block | V7 median, k puts/s | V8 Direct/400 median, k puts/s | V7/V8 ratio |
| --- | ---: | ---: | ---: |
| 1 | 46.78 | 21.37 | 2.19× |
| 2 | 49.26 | 21.37 | 2.31× |
| 3 | 49.39 | 21.35 | 2.31× |
| 4 | 49.40 | 21.41 | 2.31× |
| 5 | 48.61 | 21.15 | 2.30× |

V8's median sync count was 10.6% lower than V7's, while its median per-run
average `fdatasync` duration was about 6.6× higher. The cumulative
FRONTIER-write-plus-sync total was about 2.58× higher. These totals are
aggregate call timings, not wall-clock time saved. They are consistent with
the previously observed sync-latency difference, but aggregate counters do
not show which kernel or userspace stages cause it.

The sampled p99 ranges overlap and include substantial run-to-run variation;
this experiment does not establish a stable tail-latency result. V7's first
sample was also below its later runs, which is why both the full range and
paired block medians are shown.

## Interpretation and limits

In this same-host comparison, V8 Direct/400 remained well below V7 in Point
throughput. V8 sync count was not higher than V7's, but V8's measured
`fdatasync` and total process CPU times were substantially higher. This points
to durability and CPU-path attribution as the next work; it does not prove
either one alone is the root cause.

Using 100,000 puts divided by median throughput gives estimated measured-write
durations of 2.03 s for V7 and 4.68 s for V8, a 2.65 s difference. Dividing
median process CPU time by those estimates gives about 2.91 and 2.42 average
CPU-core equivalents, respectively. V8 therefore used more total CPU per run,
but this does not show CPU saturation on the 16-vCPU host or establish CPU
work as the critical-path cause.

The median cumulative FRONTIER-write-plus-sync difference is about 0.66 s.
Those are summed call durations, not wall time; they can overlap other work
and cannot be subtracted from the wall-time difference to calculate the
remaining bottleneck. The measurements show that neither process CPU totals
nor aggregate durability timings alone identify the serial critical path.

This test covers one host, one workload, and 16 writers. It did not run
crash-recovery qualification for Direct FRONTIER or measure other writer
counts and batches. The fixed-budget control remains benchmark-only; no
runtime default changed.

## First-pass Point attribution — 2026-11-11

The first pass used a newly provisioned `c4-standard-16-lssd` host in
`us-east1-b`: 16 vCPUs, Intel Xeon 6985P-C, two NVMe Local SSDs in RAID0, and
ext4. It ran the exact PR source commit `86361994d7dd2677bdb50a65c071c758a55b75dd`.

The workload matched the earlier comparison: 100,000 Point puts, 1 KiB values,
16 writers, V7 Parallel versus V8 Parallel Direct/400 μs. Five counterbalanced
four-run blocks alternated ABBA and BAAB order, for ten runs per arm. Broad
profiling and per-sync diagnostics were off. The only additional sampler read
per-task `stat`, `schedstat`, `status`, and `comm` files every 50 ms. Aggregate
WAL counters remained enabled.

| Metric | V7 Parallel | V8 Direct / 400 μs |
| --- | ---: | ---: |
| Throughput, median (range), k puts/s | 44.45 (43.73–46.32) | 20.35 (20.21–20.45) |
| V7/V8 throughput ratio by block | 2.16–2.23× | — |
| Sampled p50 / p99, median, ms | 0.312 / 1.759 | 0.752 / 2.444 |
| Process CPU time, median, s | 6.01 | 11.51 |
| Average CPU cores during measured writes | 2.68 | 2.34 |
| Syncs per 100k puts, median | 8,228 | 7,530 |
| Average `fdatasync` duration per advance, median | 17.7 μs | 110.0 μs |
| FRONTIER write + `fdatasync` summed time, median | 0.521 s | 1.203 s |
| Memtable insert summed time, median | 0.297 s | 0.299 s |

V8 used 1.92× the process CPU time and 2.26× the summed time inside writer WAL
submit-and-commit calls (`30.22 s` for V7, `68.33 s` for V8). These call totals
overlap across the 16 writers; they are not wall time or pure blocked time. The
average CPU use stayed below three cores for both arms, so these measurements
do not indicate machine-wide CPU saturation. The aggregate MemTable insertion
counter was nearly equal.

The scheduler and worker counters point toward extra coordination in V8. Median
voluntary context switches were 332k for V7 and 752k for V8. WAL-worker eventfd
notifications were 53.5k and 94.8k; actual eventfd writes were 17.1k and 37.7k.
The latter counter records eventfd writes when a worker is waiting, but it does
not count all kernel wakeups or identify which wakeups delay acknowledgements.
Summed run-queue wait across observed threads was 108 ms and 241 ms. The
sampler's `elapsed - runtime - run-queue wait` residual was 71.9 and 195.2
thread-seconds; this is only an approximate non-running total across threads,
includes their observed startup/shutdown lifetime, is not an off-CPU trace, and
overlaps across threads.

The Sync-I/O difference remains material: V8 had fewer sync advances, but its
median per-advance `fdatasync` duration was 6.2× higher. The median summed
FRONTIER-write-plus-sync time was 0.682 s higher for V8, while the measured
write interval was about 2.7 s longer. These call-duration sums can overlap other work, so
they cannot be subtracted from run time to assign an exact fraction of the
throughput gap to I/O. The scheduler counters likewise show correlation, not a
critical-path trace. This instrumented cohort is diagnostic only; its absolute
rates are not comparable to the earlier uninstrumented scores, and the sampled
p99 values do not qualify tail latency.

## Follow-up

The first pass makes V8's Point acknowledgement and worker-coordination path
the leading optimization candidate: it has substantially more eventfd writes,
voluntary context switches, and accumulated commit wait despite fewer syncs.
Next, use a narrowly scoped off-CPU/wakeup capture around the V8 coordinator,
I/O worker, and writer acknowledgement path to confirm which waits serialize
Point completion before changing runtime behavior.

Keep filesystem and block-layer tracing as a separate second pass to explain
the remaining `fdatasync` gap. Limit it to `fallocate`/extent changes, ext4
writeback or journal activity, and device write/flush completion. Do not combine
that capture with the scheduler pass.

A V8 sync-FD buffered-versus-`O_DIRECT` control is lower priority because the
descriptor flags do not change `fdatasync` durability semantics. If tested,
open a separate descriptor with `O_DIRECT`; `try_clone()` shares the open file
description and does not isolate descriptor flags. Treat all captures as
attribution, not performance qualification. Before any production Direct
FRONTIER change, separately qualify crash recovery and test lower writer counts
and batch workloads.

This report summarizes the original 20-run comparison and the 20-run first-pass
attribution cohort. Raw archives are not included in the PR. The temporary GCP
VM, boot disk, firewall, subnet, and VPC were destroyed after collection;
independent GCP inventory and Terraform state confirmed that no managed GCP
resources remained.

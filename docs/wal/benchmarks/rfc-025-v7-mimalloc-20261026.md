# RFC 025: System versus mimalloc allocator trials, 2026-10-26

**Result: mimalloc improves CPU-bound v7 write throughput, but neither policy passes the complete acceptance criteria. Both prototypes are reverted. System remains selected, the eleven retained optimizations remain, and v4 parity / Stage 8 remain unmet.**

The maintainer suggested the [DataFusion point-query allocator study](https://datafusion.apache.org/blog/2026/10/24/point-queries/#memory-allocator), which favors mimalloc for its workload. These measurements cover WAL point and batch writes in this engine.

## Policies and exact scope

The first prototype adds optional `mimalloc-allocator` support using [`mimalloc::MiMalloc`](https://docs.rs/mimalloc/0.1.52/mimalloc/) as the process-wide Rust allocator. Its build without that feature is byte-for-byte identical to the retained executable (`614f0cb1…`). The explicit libc `posix_memalign/free` pairs in `DirectBuf` continue to serve aligned DATA/FRONTIER buffers.

The second prototype also routes those buffers through `std::alloc::alloc/dealloc` with matching `Layout(capacity, 4096)` when selected. Capacity, alignment, pooling, reservation pins and completion ownership are preserved. A new test checks multiple capacities, contents, alignment and cross-thread destruction. Sanitizer configurations select System using the pinned nightly `cfg_sanitize` facility. These prototype changes are captured in separate patches; none remains in current Rust source.

Both use Rust wrapper **mimalloc 0.1.52**, **libmimalloc-sys 0.1.49**, and bundled native **mimalloc v3.3.2**. The optional C malloc-override feature and runtime allocator tuning are disabled. The [activation proof](artifacts/rfc-025-v7-mimalloc-20261026-allocator-proof.txt) confirms the native version. No wire bytes, hashes, WAL I/O backend, durability barrier or publication rule changes.

## Fixed protocol and results

Each policy has three RAM cells and two ext4 cells. Point cells issue 100,000 puts with eight writers or one writer; batch64 issues 750,000 puts with eight writers. All use 1-KiB values and a 2-GiB SST target, sampling latency every 100 point puts or ten batches. Each cell has four unscored warmups, then three alternating four-arm RAM rounds or five SSD rounds. Arms are System v4 / mimalloc v4 / System v7 / mimalloc v7, reversed on even rounds. SSD cooldowns are 30 seconds before each cell and ten seconds between runs; RAM uses three seconds between runs.

The two matrices preserve **152 scored records, 40 warmups, 192 unique run IDs and 1,398 clear host-process samples**. Per-command checks run before, once per second during, and after execution. No build, test or profile overlaps scoring. Sampling cannot rule out every shorter or unrelated workload, and SSD stalls remain included. The two policies are evaluated independently.

Changes below are medians of paired ratios against the same policy's System build. CPU is user plus system CPU in the benchmark measurement interval. Peak RSS is exact Linux `wait4` child-lifetime RSS, including setup and close; it has a broader scope than timed-write CPU and includes v4's post-measurement SST work. The Python launcher has its own PID and is excluded from the child RSS measure.

| Policy / cell | V4 throughput | V7 throughput | V7 CPU | V7 p99 | V7 peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| Rust heap, RAM point8 | -4.6% | +6.7% | -6.7% | -9.5% | +35.7% |
| Rust heap, RAM batch64 | +3.1% | +19.1% | +5.5% | +5.0% | +20.6% |
| Rust heap, RAM point1 | +3.6% | +5.0% | -3.8% | +14.0% | +28.2% |
| Rust heap, SSD point8 | +1.4% | +62.4% | -9.8% | -61.4% | +35.2% |
| Rust heap, SSD batch64 | +6.7% | +4.9% | +10.0% | -2.0% | +21.3% |
| Heap + aligned WAL, RAM point8 | -1.4% | +11.7% | -11.7% | +7.1% | +49.6% |
| Heap + aligned WAL, RAM batch64 | +0.1% | +18.9% | -0.5% | -18.5% | +22.4% |
| Heap + aligned WAL, RAM point1 | +0.3% | +6.5% | -5.4% | -7.2% | +37.7% |
| Heap + aligned WAL, SSD point8 | -0.1% | -0.5% | -3.4% | -18.0% | +43.1% |
| Heap + aligned WAL, SSD batch64 | +12.9% | +1.2% | +11.6% | -4.5% | +22.7% |

V4 also uses more peak memory: point workloads increase about 38–45% with the first policy and 48–54% with aligned buffers included. The full summaries retain both formats' CPU, p99, memory, medians and every paired result.

The Rust-only policy fails v7 batch CPU limits on both filesystems, v7 solo p99, and v4 SSD point p99. The aligned policy clears the v7 RAM CPU issue, but SSD v7 batch CPU rises 11.6%; v4 solo p99 rises 23.8% and SSD point p99 32.8%. Those failures reject default adoption. Planned confirmation matrices are cancelled.

The predeclared rules require each format/cell to keep paired raw and arm-median throughput at least 0.95x, CPU at most 1.05x, and p99 at most 1.10x for SSD and solo. At least one format/cell must gain 2% raw with CPU at most 1.0x. Memory over 1.20x requires investigation before retention. Normalized v7/v4 ratios remain diagnostic because both formats change allocator.

## Matching scored peaks and v4 comparison

Only scored records contribute; counts, writers, payloads and SST targets match within each row.

| Policy / workload | System v4 | Mimalloc v4 | System v7 | Mimalloc v7 |
| --- | ---: | ---: | ---: | ---: |
| Rust heap, SSD point8 | 8,991 | 17,884 | 15,940 | 16,200 |
| Rust heap, SSD batch64 | 387,380 | 413,155 | 378,176 | 376,099 |
| Heap + aligned WAL, SSD point8 | 17,672 | 17,654 | 15,896 | 16,129 |
| Heap + aligned WAL, SSD batch64 | 372,787 | 421,018 | 406,225 | 417,474 |

The Rust-only SSD point paired gain of 62.4% is heavily influenced by stalled System runs. Its highest v7 rates differ by only 1.6% (15,940 / 16,200 puts/s). Aligned buffers have nearly flat SSD point throughput and a 1.5% higher v7 peak. This does not establish the same steady SSD gain seen in RAM. The earlier retained v7 batch high of 480,373 puts/s remains a historical reference outside these matrices.

For reference, within-round median v7/v4 throughput ratios are:

| Policy / workload | System | Mimalloc |
| --- | ---: | ---: |
| Rust heap, SSD point8 | 1.863x | 2.709x |
| Rust heap, SSD batch64 | 0.939x | 0.908x |
| Heap + aligned WAL, SSD point8 | 0.887x | 0.890x |
| Heap + aligned WAL, SSD batch64 | 1.098x | 0.977x |

The [peak identity record](artifacts/rfc-025-v7-mimalloc-20261026-peaks.json) includes winning run IDs, binary hashes and raw-record hashes. Point parity remains unmet. The smaller SSD point change is consistent with durability I/O limiting that workload; this trial does not isolate each component's causal contribution.

## Memory investigation

Six separate, unscored engine-only diagnostics repeat matching RAM v7 point8/batch64 workloads with native statistics enabled only after the child forks and before it execs the engine:

| Workload | System peak RSS | Rust-only mimalloc | Including aligned WAL |
| --- | ---: | ---: | ---: |
| Point8 | 141.3 MiB | 192.1 MiB | 213.8 MiB |
| Batch64 | 905.5 MiB | 1092.7 MiB | 1111.9 MiB |

Mimalloc reports 1-GiB virtual arenas for point writes and 2 GiB for batch64. Point native peak committed counters are about 185 / 215 MiB, with about 180 / 210 MiB purged; batch native counters report about 1 GiB committed and purged. Arena reservation measures virtual address space; `wait4` measures peak resident memory. These counters and the repeated RSS increase establish a real memory tradeoff, while the short diagnostics do not qualify long-running steady-state memory behavior.

The first six diagnostic captures also inherited the stats flag into Python's launcher, producing extra native-stat output. Their records remain, are marked excluded, and are not used for memory interpretation. The corrected diagnostics set the flag inside the engine child only; System then emits no mimalloc statistics. Both sets are excluded from performance scoring. All **204 run IDs** across scoring, warmups and diagnostics are unique.

The [memory summary](artifacts/rfc-025-v7-mimalloc-20261026-memory-summary.json), [engine-only driver](artifacts/rfc-025-v7-mimalloc-20261026-memory-probe-engine.py), [manifest](artifacts/rfc-025-v7-mimalloc-20261026-memory-probe-engine-runs.tsv), [raw records](artifacts/rfc-025-v7-mimalloc-20261026-memory-probe-engine.jsonl) and [host audit](artifacts/rfc-025-v7-mimalloc-20261026-memory-probe-engine-host.jsonl) preserve the diagnostic evidence and native stats file hashes.
